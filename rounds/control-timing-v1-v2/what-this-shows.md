# Timing control, v1 × v2 — what it shows, and what it does not (11/09/2026)

Read with `expected.md` (the design and the rule for "faster", fixed before the runs) and `transcript.md` (the runs, the counters, the four answers).

**On the fixture, with everything but the instructions held equal, the two runs per version cannot see a difference in time.** v1 took 3 min 19 s – 3 min 30 s (corrected on 11/09 after the author's assistant read the session's trace: the file first said 3 min 05 s – 3 min 15 s, a window in which the run had not yet ended; that run's start is also an estimate, the only one of the four) and 3 min 33 s – 3 min 43 s; v2 took 3 min 14 s – 4 min 24 s and 2 min 47 s – 3 min 00 s (the upper bound of the second is the JS confirmation at 14:49:27; the table of `transcript.md` named 14:49:24 as its endpoint until 11/09 evening, which did not match the figure derived beside it, and now names the one the figure comes from). The rule written before the runs said "v2 is faster" only if both v2 runs are shorter than both v1 runs; the first v2 run's range overlaps both v1 runs (and was measured more coarsely, declared), so the verdict, recomputed with the corrected figure, is the third one the rule allows: **no difference the two runs can see**. This is what the prediction expected ("v2 costs about the same; the CSV block is the visible extra"): v2's answer is about twice as long (≈8.6k characters against ≈3.9k), because its rules add the CSV block with the full location, and it took no longer.

**Tool calls and files read.** v1: 7 commands + 5 files, then 4 + 5 (12 and 9 steps). v2: 2 commands + 6 files, then 4 + 4 (8 and 8 steps). Both v2 runs took fewer steps than both v1 runs; the difference is small and the counters are the interface's summary, not a trace. The files v1 read were the same five in both runs (rules, identity, examples twice, the index, the note); v2's are not listed by the interface in the same way. Nothing here separates "fewer steps" from noise with two runs per cell.

**Shape and result.** All four runs returned the FAIL on the service code and the same seven other results; the two v2 runs returned the revised shape (label in the check cell, who acts in the severity cell, short location, CSV block) on the first try each time, as the run of 10/09 had. One English sentence of the model's own preceded the report in one run of each version — a habit of the model, not of a version.

**The real-note pair did not run.** The design's runs 5–8 (the client's note of rounds 1 and 2, numbers only) were stopped before the first send: the session's tool classifier refused to attach the client's note to the chat on the author's account. The author decided, later the same day, **not to run it**: the client's note never enters this repository, and the pair answers none of the four questions of the brief. Nothing of the note was sent, and nothing of it is here.

**What this control does not prove.** Two runs per cell, on one note, on one account, in one hour; the clock is the page's, read every ten seconds, so every time is a range; the counters are the interface's summary. It does not measure the Employee's time (that is `round-2-v2/time.md`, with its own caveats), and it does not say which of the four changes between round 1 and round 2 made her reading faster. What it does say is narrow and holds: with model, effort, route and input fixed, the v2 instructions produce the longer, revised report in about the same time as the v1 instructions produced the old one, with no more steps.

## The v2 folder changed after these runs — what changed, and when (added 11/09/2026, evening)
This control compares the **v1 instructions** against the **v2 instructions as they stood when the four runs happened**. The folder has been corrected several times since, through the day and the evening of 11/09/2026, so the folder published at the tip of this repository is no longer byte-for-byte the one these runs used. Every correction is listed, each against what the operator hit and each with its commit, in the table of `../round-2-v2/what-changed.md`; the state these runs used is the tree at commit `88063b8`, which git keeps. **No correction changes a number, a check, a result or the verdict on this page.** This section is not a count, on purpose: the set it describes grew four times today, and a number written here would have been false before the deadline.

**What of it touches this control.** Some of the corrections are inside the auditor's own rules. The sentence printed above the CSV block now also forbids pasting the block straight into Excel, which is a line of text the report prints. The location cell and the CSV block may no longer carry the taker's registered company name, which changes what one cell of one row is allowed to contain; the four runs on this page predate it. The rest are steps of the README, which no run reads.

**And the loaded folder itself is no longer the one these runs uploaded** (written 11/09/2026, evening). Three things changed in the set of files the operator loads, after these runs: `examples.md` lost the English twin of each worked example, which moved to `rounds/fixture-runs-v1/report-all-runs.md`; the output contract left `rules.md` § 3 for a new top-level file, `output-contract.md`; and that file joined the load list, so the folder went from fifty-three files to fifty-four. This page is the one whose declared job is to say that the published folder is not the measured folder, so it says it here too, and not only in `../round-2-v2/what-changed.md`. The instructions these runs compared are the v2 instructions of that morning, and `88063b8` is where they are.
